# SpeedyWeather

This folder contains **two independent environments** for two different
purposes — don't assume it's all one Julia project.

## 1. Main simulation (Julia)

`run_tests.ipynb` runs the actual SpeedyWeather
transformation tests: it initializes a baroclinic-wave simulation,
applies three grid transformations (rotate longitude, reverse latitude,
reverse longitude), runs each for 10 days, and measures how much the result
differs from an untransformed baseline once transformed back. It writes three
`.nc` error files to `../data/SpeedyWeather/saved_errors/`.

**Julia 1.11** — `Manifest.toml` was resolved on 1.11.5, and IJulia builds the
kernel name from the running Julia version, so 1.11 is what this notebook's saved
kernel (`julia-speedyweather-release-1.11`) refers to. On another minor version
you would get a differently-named kernel and Julia would re-resolve the manifest,
which is the thing the pinning is there to prevent.

Setup:
```bash
cd SpeedyWeather   # this folder
julia --project=. -e 'using Pkg; Pkg.instantiate()'
julia --project=. -e 'using IJulia; IJulia.installkernel("Julia SpeedyWeather release", "--project=" * pwd())'
```
Then open `run_tests.ipynb` in Jupyter and select
the "Julia SpeedyWeather release" kernel. Runs in a few minutes on a modern
multi-core machine (4 full 10-day simulations).

Package versions are pinned in `Project.toml`/`Manifest.toml` to match the
exact versions originally used (`SpeedyWeather 0.19.0`, `CairoMakie 0.15.10`).
**Note:** because this test measures errors at ~1e-13 K (machine-epsilon
level), re-running it on different hardware will reproduce the same
qualitative result but not the exact same floating-point digits as the
published figure — this is a fundamental cross-machine floating-point
reproducibility limit, not something environment pinning can fix (confirmed
by testing). See the note cell at the end of the notebook, and part 2 below
if you need the exact published figure.

## 2. Reproduce the published figure exactly (Python)

`reproduce_published_figure/` is a separate, self-contained Python notebook
that reads the **original** `.nc` files that actually produced the published
figure `speedyweather_rmse_vs_leadtime.jpeg` (**Figure 9** of the paper; bundled at
`../data/SpeedyWeather/paper_original/`, not regenerated by the notebook
above) and re-plots them with the exact plotting code used in the paper.

**Data source:** the original `.nc` files are pulled from Zenodo automatically
if they are not already present locally — the notebook checks `DATA_DIR` and
downloads and checksum-verifies anything missing. The record is named by the
`ZENODO_RECORD_SPEEDYWEATHER` variable in the notebook's config cell; if you
would rather supply the files yourself, put them in `DATA_DIR` and the download
is skipped.

Setup — **Python 3.11 or 3.12.** The pinned versions were resolved and validated on 3.12,
and re-checked to resolve identically on 3.11. Anything older will fail: several
of the pins require 3.11 or newer. If the machine has neither, `uv` can install a
Python without root — `curl -LsSf https://astral.sh/uv/install.sh | sh`, then
`uv python install 3.12` and `uv venv --python 3.12 env`.

The quickest way is to let the script do it — it finds a suitable interpreter
(or installs one via `uv` if you have neither), builds the environment from
`requirements.lock`, and registers the kernel:

```bash
cd SpeedyWeather/reproduce_published_figure
./setup.sh
```

On a cluster, note that `setup.sh` deliberately keeps `uv`'s interpreters and
all wheel caches in `.uv/` at the repository root rather than the usual
`~/.local` and `~/.cache`. A quota'd home directory is the normal case there,
and a per-user quota is invisible to `df`, so the install would otherwise pass
the free-space check and then fail partway with "Disk quota exceeded". Set
`UV_PYTHON_INSTALL_DIR`, `UV_CACHE_DIR` or `PIP_CACHE_DIR` to override.

By hand instead: check the interpreter first, and chain the steps, so a missing
one stops the sequence rather than quietly installing into whatever environment
is already active:

```bash
python3 --version   # must be 3.11 or 3.12; otherwise name one, e.g. python3.11
```

```bash
cd SpeedyWeather/reproduce_published_figure && \
python3 -m venv env && \
source env/bin/activate && \
pip install -r requirements.lock && \
python -m ipykernel install --user --name speedyweather-repro-env --display-name "SpeedyWeather repro (Python)"
```

**`requirements.lock` vs `requirements.txt`.** The lock file is the fully
resolved environment — all 42 packages, including the transitive ones
`requirements.txt` leaves to pip's resolver, which drift as PyPI moves. Install
the lock; read `requirements.txt`, which stays the hand-maintained list of the
5 direct pins. Regenerating the lock, if you ever change a pin, needs `uv` —
the command is in the lock file's own header.

This is the cheapest environment in the repository — 5 dependencies, ~9MB of
data, no GPU — so it is a good first test that a new machine works before
committing to GraphCast's 6.4GB install.
Then open `plot_published_figure.ipynb` and select that kernel.

## Why two environments?

The Julia notebook is the actual research code — useful if you want to verify
the SpeedyWeather pipeline runs and produces sensible (near-zero)
errors on your own machine. The Python notebook exists only because that
simulation can't be bit-reproduced across machines at the precision this test
operates at, so getting the *exact* published figure requires starting from
the *exact* original data rather than a fresh run.
